# 离线档案断链核查

馆员出借旧网站离线档案前，用本工具核查哪些链接会断：

1. **上传抓存目录 CSV**——每行列明页面地址（完整 URL）、UTC 抓存时刻、同站出链（完整 URL）；
2. **选入口和回看时刻**——从入口沿同站出链逐页核查，每个 URL 取不晚于回看时刻的最近一条抓存，互链页面只查一遍；
3. **保存结论**——列出缺档 URL 及从入口走到它的路径；
4. **补传联动**——补传改变了核查所选的抓存，或为原缺档 URL 补上了可用记录时，相应结论自动标为「待复查」；其余补传不影响结论有效性。

## 启动

### Docker Compose（推荐）

```bash
docker compose up --build
# 打开 http://localhost:8000
```

SQLite 数据库保存在命名卷 `archive_data` 里，容器重启后结论仍可查。

### 本地运行

```bash
pip install -r requirements.txt
python wsgi.py          # http://localhost:8000
```

环境变量：

| 变量 | 默认 | 说明 |
|---|---|---|
| `ARCHIVE_DB` | `instance/archive.db` | SQLite 数据库路径 |
| `SECRET_KEY` | `dev-only-secret` | Flask 会话密钥，生产请覆盖 |
| `CHECK_STEP_DELAY_MS` | `0` | 核查每处理一页 sleep 的毫秒数（演示/测试交错操作用） |

## CSV 格式

表头须包含三列：`url,captured_at,outlinks`

```csv
url,captured_at,outlinks
http://old.site/,2023-01-05T08:00:00Z,http://old.site/about|http://old.site/news
http://old.site/about,2023-01-05T08:01:00Z,http://old.site/
http://old.site/news,2023-01-05T08:02:00Z,http://old.site/news/item-1|http://old.site/news/item-2
```

- `url` / `outlinks`：完整 URL（http/https）。多个出链用 `|` 分隔，或用 JSON 数组；无出链留空。
- `captured_at`：ISO 8601 时间；无时区时按 UTC 处理。
- 同一 URL 可有多行（不同时刻的多份抓存）。

`sample_data/` 里有四个示例，演示顺序见下文「演示：乱序补传与核查」。

## 一致性规则

- **冲突整批退回**：同一 URL 同一时刻的记录，若出链与既有档案（或同批内另一行）不同，整批退回，不写入任何记录；完全相同的记录自动跳过。退回也留痕可查。出链一律按**还原后**的完整内容比对（见下节）。
- **批次与结论状态同步生效**：目录入库与受影响结论的「待复查」标记在同一个事务里完成；任一步写入失败，目录与结论标记均保留原状。
- **待复查的触发条件（且仅这两个）**：
  1. 结论中某页面出现了更晚但仍不晚于回看时刻的抓存（核查所选会变）；
  2. 结论中的缺档 URL 出现了不晚于回看时刻的抓存（缺档被补上）。
- **交错操作不留过时结论**：核查遍历在同一只读快照事务中进行（WAL 模式下不阻塞补传）；结论落库时在写事务里复查快照之后新生效的批次，若影响本结论则直接标为「待复查」；补传事务也会扫描全部有效结论。两个机制互补，任何交错顺序下都不会留下过时的「有效」结论。
- **遍历期间可补传**：SQLite WAL + 多线程服务器，长核查请求期间上传请求照常处理。

## 出链差量存储

同一页面历次抓存往往只换几条出链，因此新入库的抓存不逐版存完整 JSON，而是优先存**相对既有抓存的差量**：

- `captures` 行要么是**完整快照**（`base_id` 为 NULL，`outlinks` 存完整 JSON），要么是**差量行**（`base_id` 指向基抓存，`delta_add`/`delta_remove` 记录相对基的增删）。
- 新抓存的基从同 URL **时间相邻**（前驱/后继各取 2 条）且链深未满的既有抓存中选差量最小者；差量载荷严格小于完整 JSON 才存差量，否则存完整快照（即"重基"）。
- **还原上限**：链深（`depth`）不超过 8，还原任意一次抓存最多读取 8 条抓存的出链载荷。
- **乱序补传**：抓存只插不改。补传旧时点的记录时，新行以既有相邻抓存为基存差量，**已存载荷原样保留**。
- **旧库兼容**：旧库的抓存行没有差量列，迁移（启动时自动 `ALTER TABLE` 补列）后 `base_id` 为 NULL，即完整快照，可直接被读取、也可被选作新抓存的差量基，无需改写任何既有数据。
- 重复/冲突判定、核查遍历、批次详情统一经 `load_outlinks` 还原完整出链；核查选档规则（不晚于回看时刻的最近一条）不变。
- 首页与批次详情页显示出链载荷合计 vs 逐版完整 JSON 的对比。

**基准**：同一 URL 120 次抓存、每次 40 条等长出链、相邻两次只换一条，按抓存时刻导入空库，出链载荷合计约为逐版存完整 JSON 的 **17%**（要求 < 50%），最大链深 8。复现：

```bash
python3 scripts/gen_delta_benchmark.py /tmp/bench.csv 120   # 生成基准目录
# 在网页上传 /tmp/bench.csv，首页即显示载荷对比；或运行：
python3 -m pytest tests/test_delta.py -q
```

## 演示：乱序补传与核查

`sample_data/` 里有四个示例：`catalog_v1.csv`（首传）、`catalog_v2_supplement.csv`（补传）、`catalog_backfill_older.csv`（**乱序补传旧时点**：2023-01-04 的抓存，早于库中 2023-01-05 的既有记录）、`catalog_conflict.csv`（冲突示例）。

按以下顺序在网页操作即可看到完整联动：

1. 上传 `catalog_v1.csv`；以入口 `http://old.site/`、回看时刻 `2023-06-01T00:00` 核查 → `news/item-2` 缺档；
2. 上传 `catalog_v2_supplement.csv`（补上 item-2）→ 结论 #1 自动标「待复查」；
3. 上传 `catalog_backfill_older.csv`（乱序补传更早的 2023-01-04 抓存）→ 批次详情可见新行以**差量**存储、既有行原样未动；结论 #1 不受影响（补的是更旧的抓存，不改变其选档）；
4. 以回看时刻 `2023-01-04T12:00` 再核查 → 使用补传的旧抓存，`news/item-1` 在该时点尚无抓存而判缺档；
5. 上传 `catalog_conflict.csv` → 与既有档案同 URL 同时刻出链不同，整批退回并留痕。

## 测试

```bash
pip install -r requirements-dev.txt
python -m pytest tests/ -q
```

覆盖：断链识别与路径、回看时刻选抓存、互链去重、补传标复查（两类触发 + 无关补传不误标）、冲突整批退回、交错核查、重启持久化、页面冒烟；差量存储专项：120 版基准（载荷 < 一半、还原 ≤ 8 条载荷）、乱序补传不改已存载荷、按还原后出链判重/判冲突、旧库迁移即用、核查与批次详情走还原出链。

## 已知限制

- 出链是否"同站"由上传的 CSV 保证，核查时不再额外过滤。
- 单进程多线程 + SQLite，适合馆内部署；多实例水平扩展需换外部数据库。
- 极大目录（百万行级）上传为一次性解析，内存随文件大小增长。
